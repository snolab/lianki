# i18n: every string carries its context

Lianki's UI strings live in intlayer content declarations (`*.content.ts`),
16 locales each (`intlayer.config.ts`). The app's own config for
`intlayer fill` is in [AI_TRANSLATION.md](AI_TRANSLATION.md).

## The rule (owner, 2026-10-30)

**Never translate a short string in isolation.** A setting name, a menu item,
a button or a logo text sent to translation alone loses its meaning: "Undo"
can come out as "Cancel", "New swipe" as "a new swipe", "Experimental" as an
adjective about one item instead of a section heading. Every string carries
context, and is translated together with it:

- **where it appears** — the page, the part of the screen, the kind of element
  (button, on/off switch, toolbar link, tooltip, screen-reader label, dialog);
- **what it is for** — what the action does or what the item means;
- **how it is used** — grammar (imperative verb, noun, past participle and
  what it agrees with), length limits, and what to keep as is
  (`{placeholders}`, keyboard keys, arrows, product names).

## Writing a string

intlayer 8 has no per-key metadata; a dictionary's `description` is what
`intlayer fill` passes to the translating model as context
(`dictionaryDescription`). So each content file keeps a `context` record — one
line per key — and builds the description from it with
`describeKeys(about, context)` (`lib/i18n-context.ts`):

```ts
const dictionary = {
  key: "words-page",
  content: {
    undo: t({ en: "Undo", fr: "Annuler", … }),
  },
};

const context: Record<keyof typeof dictionary.content, string> = {
  undo: "Button in the toast shown after a list was deleted: brings the list back. Undo, not Cancel.",
};

export default {
  ...dictionary,
  title: "/words — word lists and the study view",
  description: describeKeys("What this dictionary covers, and rules for all of it.", context),
} satisfies DeclarationContent;
```

Typing `context` as `Record<keyof typeof dictionary.content, string>` makes a key without
context a type error. `unit/i18n-context.test.ts` also fails on a missing,
stale or too-thin line (under five words, or just the English repeated).
Add a dictionary to that test's list when it adopts the pattern.

Nested content (groups such as `metadata`, `errors`, `features.fsrs`) takes a
`context` of the same shape, typed `KeyContext<typeof dictionary.content>`
(one string per `t()` leaf, so a missing one is a type error), and
`flattenContext(context)` turns it into `group.key` lines for `describeKeys`.

The description stays out of the runtime bundle: intlayer keeps it only in
`.intlayer/unmerged_dictionary` (read by `fill`), not in the dictionaries
`useIntlayer` loads.

## Translating (agents and `intlayer fill`)

- Read the key's context line before translating it, every time, and
  translate the English and its context together. Batch strings of one screen
  so they stay consistent with each other (grade names, the word for "due").
- Match what the context says the string is: a button is a verb, a switch name
  is a short noun phrase, a section heading names a group of features.
- Prefer the platform's own terms where the context names them (iOS menu
  names, Anki's grade names in that language).
- When reviewing a translation, check it against the context, not only the
  English: a one-word label that reads right alone can read wrong on its
  button.
- A new key gets its context line in the same change — never "add context
  later".

## Product names

Names stay as they are in every locale; a context line that contains one says
so.

| Name    | What it names                                                                                                                                            | In every locale               |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| Lianki  | the app                                                                                                                                                  | Lianki                        |
| LiCards | turning web pages into cards: page cards, the userscript widget, the review flow without the userscript and the bookmarklet (owner decision, 2026-11-01) | LiCards — except zh: **链卡** |

"LiCards" names the feature, not a single card: one saved page is still "a
card" ("save this page as a card"). Code identifiers, routes, API paths and
storage keys keep their old names (`group: "advanced"`, `/list`, `/next`).
